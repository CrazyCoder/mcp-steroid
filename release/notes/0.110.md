## 0.110

This release adds two tools that change how an agent works with the IDE. In the original MCP Steroid, an agent had two ways in. It could write a Kotlin script for `steroid_execute_code`, which compiles for several seconds on every call, or it could read screenshots and click at pixel positions. Both cost many turns for common jobs such as a rename, a Settings change or a dialog.

- `steroid_ui` reads the IDE's windows as text and drives them by what they show. It compiles no code, so a call answers in well under a second.
- `steroid_take_screenshot` with `marks=true` labels every interactive control on the picture with a ref that `steroid_ui` acts on, so what the agent sees is what it can click.
- `steroid_refactor` runs rename, safe delete, move, quick fixes, intentions, import optimization, reformat and find usages without a script. It shows what a change would do before it makes it, and it does not disturb a person who works in the same IDE.

`steroid_execute_code` also got safer: a write action in a script no longer freezes the IDE on 2026.2, and the agent is told when the IDE is busy in the background.

### Screenshots the agent can act on

`steroid_take_screenshot` with `marks=true` outlines every interactive control on the image and labels it with its ref, such as `e12`. These are the refs `steroid_ui` uses, so the agent reads a ref off the picture and acts on it: `{"action":"click","ref":"e12"}`, or `fill`, `select`, `check`, `inspect`.

In the original MCP Steroid, a control seen on a screenshot could only be clicked at its pixel position. The agent had to measure the position, divide it by the display scale, and click again when the layout moved. A ref needs no arithmetic, still finds the control after a resize or scroll, and the step reports what the click caused. Coordinates remain for what has no ref, such as a web view, a canvas or a drag. The tool descriptions and recipes now steer agents to refs first.

Only the part of a control that is in view is marked, so a control scrolled out of sight is not outlined over the controls the picture shows.

### steroid_ui: read and drive the UI as text

- A call with no steps returns a snapshot of the project's showing windows, topmost first. Each line is one control: its class, accessible name, a ref such as `[ref=e12]`, states such as `[disabled]` or `[checked]`, the value of a text field or combo box, painted text such as tab titles, the tooltip, and the caption before an unnamed field. Lists, trees and tables show their rows in view with index, tree depth and state. The agent reads exact names and states instead of guessing them from a picture.
- Steps act on controls by ref, name, text, class or XPath: `click`, `hover`, `type`, `fill`, `press`, `check`, `uncheck`, `select`, `close`, `wait` and `snapshot`. Each step reports what it caused: where the press landed, which IDE action ran, which windows opened or closed, and where the focus went. The response then shows only what changed, so a sequence of steps does not repeat the whole window.
- `select` picks a list, tree, table or combo row through the selection, as the keyboard does, so a list that acts on a click, such as Find Action, does not run the row. A tree row can be named by its path, such as `Editor > General > Appearance`.
- A step that opens a dialog waits for it. A button or action whose name ends with an ellipsis waits up to 10 s for its window, and a window that opens later is reported by the next step as "meanwhile opened". A click that opens a modal dialog returns while the dialog is up.
- The first failing step stops the run and shows the topmost window with the nearest matching controls, so the agent can correct the target in one more call.
- Settings works in IntelliJ IDEA 2026.2, where it opens as a separate window.
- `goto` opens a file at a symbol, a line and column, or an exact snippet, and `run` runs any IDE action by its ID there. Together they reach the refactorings that have a dialog or an in-place template, such as Change Signature, Extract and Inline, in any language. `run` reports a disabled action, an unknown ID with similar IDs, and an in-place template to type into.
- `inspect` tells where a control comes from, as the IDE's UI Inspector does in internal mode, but in two lines and in any IDE: its class and owning plugin, the action behind it with its class and plugin, the tool window it sits in or opens, its dialog class, model and renderer, and the code that created it. For a row it gives the value and user object classes, the action behind a popup or Search Everywhere item, the intention or quick fix behind an Alt+Enter item, and a Settings page's configurable class and ID. This answers "which plugin or class owns this UI" in one call. The inspector's own property list is about 3 KB per control, and `inspect` reports what locates the code in a few hundred characters.
- Snapshots show `action=<id>` on toolbar buttons and menu items, so the agent can `run` the action instead of clicking.
- `trace: true` keeps a picture of the topmost window before and after each step, with the snapshots and events, in the execution folder. Use it as reproduction evidence.
- Scripts get the same engine: the `ui.*` helpers of `steroid_execute_code` take the same targets and refs, and `ui.open { }` shows a dialog and returns it while the script keeps running.
- `steroid_execute_code` has a new `modal=dialog` mode. The script runs under the open modal dialog's modality, so it can read and change the dialog's state while the dialog stays open.

### steroid_refactor: refactorings without a script

- Operations: `rename`, `safe_delete`, `move` (a file into a directory, with package statements updated where the language has them), `fix` (an inspection's quick fix), `intention`, `optimize_imports`, `reformat` and `usages`. The target is a file with a symbol name or a line and column. It resolves through the IDE's code model, so every reference is updated, in the languages the IDE understands. It was tested on Kotlin, JavaScript, TypeScript and Rust.
- Every call is a dry run unless `apply` is true. The dry run lists the element and its usages as `path:line: text`.
  - For `rename`, it lists the lines the rename would change, the references it leaves alone (such as a Markdown code span), the conflicts, and declarations of the new name in the same scope, which a language without a clash check does not report.
  - For `optimize_imports` and `reformat`, it applies the change to a copy and reports the lines it would add and remove.
  - For `fix` without an inspection name, it lists what every enabled inspection reports in the file, with short names and severities, from WEAK WARNING up as the editor highlights them. `all: true` adds the INFORMATION-level suggestions. An unknown inspection name answers with similar names.
- An applied change reports each changed file with the lines added and removed. Edit > Undo takes it back as one step named "MCP Steroid: ...". A refactoring with conflicts returns them and changes nothing. A failure reports what it changed before it stopped.
- It stays out of the way of a person working in the same IDE. It opens no dialog and no editor tab, it moves no caret and no focus, and it saves only the files it changed, so the person's unsaved edits elsewhere stay unsaved.
- A `symbol` target skips its occurrences in comments. The response says which occurrence it took.
- A JavaScript export of the same name, such as `module.exports = { name }`, counts as an alias. `usages` lists the callers that reach the function through it. A rename dry run from the function lists the callers it leaves alone, and one from the export shows that it renames the function too.
- Usages in injected code, such as a JavaScript block in Markdown, show the host file and line.
- After a start or a project sync, the IDE runs background tasks, such as a Cargo reload or Rust name resolution, and references come back partial while they run. The tool waits up to 30 s for them, once for a task that keeps running, and names any that still run.
- Most operations finish in under a second.

### steroid_execute_code

- `writeAction { }` in a script runs on the EDT inside one command named "MCP Steroid script". On 2026.2 it ran on a background thread. There, a Kotlin quick fix inside it leaked the write lock and froze the IDE until it was killed, and EDT-only calls such as `commitAllDocuments()` threw. Each write is also one undo step now.
- When the IDE runs background tasks, such as indexing, a project sync or name resolution, the response starts with a note that names them. The agent knows that references and inspections can be incomplete and can wait. `steroid_list_windows` lists them as `backgroundTasks`.
- When a modal progress, such as a project open, blocks a non-modal script, the error names it and says that it ends on its own.

### Recipes

- The rename, safe delete, move, quick fix, find usages, optimize imports and formatting recipes lead with `steroid_refactor`. The UI recipes lead with `steroid_ui`.
- A new recipe, `mcp-steroid://ide/project-structure`, adds a module with its content root, source roots and excluded folders, as File | Project Structure does, without the dialog.
- The coding guide says that a plugin's content modules are on the script classpath, so their classes can be imported directly. A plugin's own class loader loads only its main module.
- The quick fix recipe applies the fix on the EDT inside one command, as the editor does. It applied the fix inside `writeAction { }`, which froze the IDE for most Kotlin fixes. The safe delete, move and rename recipes no longer commit documents after the refactoring, which threw on 2026.2.

### Other fixes

- In Split Mode, the JetBrains Client no longer logs an error about VCS classes at every start.
